# Start here

This guide assumes you know wastewater treatment but not this software. No programming is needed beyond typing a few commands.

## What is this?

AERA is a computer model of an activated sludge works. **Shadow mode** takes your own recorded data, replays it through the model, and answers two questions:

1. **Can the model be trusted on your works?** It runs your recorded flows and loads through the model, and checks the result against what your works really recorded. To be called **validated** it must reproduce both your effluent ammonium and the day-to-day shape of your blower energy. If they do not match, or if one cannot be checked, it says so, and everything else is labelled research only.
2. **What would change if the dissolved oxygen (DO) setpoint were different?** Energy, cost, carbon, effluent ammonium, and your permit limits, side by side.

It gives **advice only**. It never connects to your plant, your SCADA or your historian, and it cannot change a setting. You give it a file; it gives you a report. The analysis code makes no network connections. (The only network-facing code is a read-only web page for the report in the web app, which you do not need to run.)

## What it does not do

- It does not know your works. It uses a generic benchmark plant (the IWA "BSM1" activated sludge plant), scaled to your flow. Your tank layout, aeration system and settlers are different. That is why the model check comes first.
- It models temperature only through typical literature coefficients, which are not fitted to your works. If you record the mixed liquor temperature it follows it; if you do not it assumes a constant (15 degrees Celsius unless you set `temperature_c`), and in cold weather that makes it too optimistic.
- It is not a statement of permit compliance. It indicates risk, using daily averages, not your permit's sampling.
- It has no data from a real works yet. It was built and tested on a synthetic works. A pilot on real data is the next step (see docs/FOR_WATER_COMPANIES.md).

## Setup (once)

You need Python 3.13 and `uv`. In a terminal, in the project folder:

    uv venv --python 3.13
    uv pip install -r requirements.txt
    .venv/bin/python scripts/fetch_bsm1.py

The last line downloads the public IWA benchmark files (checksum verified, about 14 MB). They are needed for the demo and for the model's weather files.

## Path A: see it in 5 minutes

    .venv/bin/python -m aera.site demo --out demo_site

This creates a **synthetic** works (fake data, clearly labelled), runs shadow mode on it, and writes `demo_site/shadow_report/report.html`. Open that file in a browser. It takes about 3 minutes.

The synthetic data is generated by the same model that then replays it, so the fit is artificially good. Real data will fit worse. To see what a bad fit looks like:

    .venv/bin/python -m aera.site demo --out demo_bad --mismatch 0.4

The report will say the model does NOT reproduce the data, and the recommendation becomes "research only".

You can also see the page in the web app: run `./start.sh`, open http://127.0.0.1:5161 and choose **Shadow mode**.

## Path B: your own data

### 1. Get the data

Export a CSV from your historian covering **at least 3 weeks** at 5 to 15 minute intervals, ideally including a wet weather event. One row per time step, one column per measurement. You need:

| Needed | Measurement | Why |
| --- | --- | --- |
| Yes | Flow entering the biological treatment | The model's main input |
| Yes | Ammonium entering the biological treatment | The model's main load |
| Helpful | Influent COD | Better load description |
| Helpful | Effluent ammonium | Lets the model be checked |
| Helpful | Blower power (kW) | Lets energy be calibrated and checked |
| Helpful | DO in the last aerated zone | A second check of the model |
| Strongly recommended | Mixed liquor temperature | Nitrification slows sharply in the cold. Without it the model assumes a constant temperature, and in winter it will over-predict how well your works nitrifies |

Without effluent ammonium and blower power, the model cannot be fully validated: with only one of them the report says "partly validated", with neither it says "cannot validate". Recorded effluent ammonium that barely varies (for example a constant lab value) cannot test the model either, and is reported as not scored.

Do not clean the file. The tool reports what is wrong with it and never changes your original.

### 2. Create the settings file

    .venv/bin/python -m aera.site init my_works

This creates `my_works/site.toml`. Copy your CSV into `my_works/`. Open `site.toml` in any text editor. Every setting has a comment. The ones you must change:

- `design_flow_m3_d`: your average dry weather flow in m3/d.
- `[data] file`: the name of your CSV. `timestamp_is_local`: true if times are local clock time (most exports), false if UTC or if they carry an offset such as +01:00. UK dates (31/10/2026) and ISO dates (2026-10-31) are both understood; if yours are different, set `timestamp_format`.
- `[data.tags.*]`: for each measurement, the **column name** in your CSV and its **unit**. Units understood: flow m3/d, m3/h, l/s, Ml/d; concentrations mg/l, g/m3, ug/l; power kW, W, MW.
- `[site] temperature_c`: the temperature to assume if you have no temperature record (default 15). Better still, add `[data.tags.temperature]` with your probe's column.
- `[control]`: how you control DO today (setpoint and, if known, gains).
- `[[consent]]`: copy the limits from **your own permit** (see "Permit limits" below).
- `[tariff]` and `[carbon]`: your electricity price and the current UK government carbon factor. The defaults in the file are placeholders.

### 3. Check the data

    .venv/bin/python -m aera.site check my_works/site.toml

This reads your file and prints a plain report: how much usable data each measurement has, what was removed and why, gaps, and the periods long enough to replay. **Read it.** Typical findings:

| Message | What it means | What to do |
| --- | --- | --- |
| Median influent flow is N times the design flow | A unit is probably wrong | Check the flow unit and `design_flow_m3_d` |
| value(s) in a stuck sensor run | A probe froze on one value (judged in hours from your file's time step) | Nothing; those values were ignored. If a constant value is normal for a tag (a lab result held until the next sample), list it in `flatline_exempt` |
| longest gap after filling is N hours | A sensor was offline | Gaps up to `max_fill_hours` are filled completely; longer ones stay empty, and a key tag with a long gap splits the replayable periods |
| repeated local timestamps resolved as the autumn clock change | Normal for local time exports | Nothing |
| No continuous period of at least 7 days | Gaps break the data into short pieces | Export a longer, more complete period |

### 4. Run shadow mode

    .venv/bin/python -m aera.site replay my_works/site.toml --candidate so_ref=1.7 --sweep 1.0,1.5,2.0,2.5,3.0

`--candidate` is the setting you want to test (here a DO setpoint of 1.7 mg/l). `--sweep` compares several setpoints. Both are optional. It takes a few minutes. The report is `my_works/shadow_report/report.html`.

### 5. Read the report

Read it top to bottom:

1. **The two banners.** The first says whether the model matches your records. If it says NOT validated, stop: do not use the numbers.
2. **Does the model match your records?** For each indicator, how well the model follows what you recorded, marked pass, FAIL or *not scored*. *Nash-Sutcliffe* is 1 for a perfect match and 0 for "no better than the average". *Bias* is the average error in per cent. The energy check tests day-to-day shape only (the model's energy level is scaled to your blowers, and a scaling outside the believable range fails). The DO check is weak, because the model is driven to the setpoint you configured. The pass marks are the author's choice, not a standard; you can change them in `[validation]`.
3. **Permit-style limits.** Modelled effluent against your configured limits, for today's control and the candidate.
4. **Energy, cost and carbon.** Today against candidate, with a price range that reflects only the tariff and carbon-factor uncertainty you configured, not model error. Annual figures are extrapolated and only meaningful if your window is typical of the year.
5. **The setpoint sweep.** The trade-off: more air costs energy and lowers ammonium. Find the lowest setpoint that keeps every limit.
6. **What this does not tell you.** Read it. It is the honest list of assumptions.

### 6. Calibrate the model to your works (optional, recommended)

If the model is not validated, or even if it is, you can let the tool fit the model to your data first:

    .venv/bin/python -m aera.site replay my_works/site.toml --candidate so_ref=1.7 --calibrate

It fits two multipliers on the benchmark plant to your first 60% of days: **nitrifier activity** (how fast the plant converts ammonium; recorded effluent ammonium tells us this) and **oxygen transfer efficiency** (fouling and diffuser condition; recorded blower energy tells us this). Then it checks the fit on the other 40% of days, which the fit never saw. The report says what was fitted, how much the held-out ammonium error fell, and the model check that follows is judged on those held-out days only, so a calibration cannot grade its own homework.

It is built to refuse: a parameter your data cannot identify is left at 1.0 (not fitted to noise), and a fit that does not cut the held-out ammonium error by at least 10% (or that makes the energy shape worse) is **not used**, and the benchmark plant is kept. You need effluent ammonium recorded, and at least 3 weeks of data (about 7 days to fit and 7 held out, after 3 days of warm-up). It takes about 6 minutes for three weeks of data on an 8-core machine.

It fits only those two parameters. It cannot fix a works whose layout is different from the benchmark (see below). Settings are in `[calibration]` in `site.toml`.

### 7. If the model is "not validated" (even after calibration)

This is common and useful: it tells you the model does not describe your works, instead of giving you a confident wrong answer. Typical causes, in order of likelihood:

1. A unit or tag is wrong. Re-run `check` and read the warnings.
2. The sensor data is poor (drift, long gaps).
3. Your works differs from the benchmark layout (for example trickling filters, a different aeration scheme, high return liquor loads). Calibration of two multipliers cannot fix this; see docs/ROADMAP.md.
4. Calibration may help: use `--calibrate` (step 6). If it is refused or still not validated, the plant structure is probably wrong for your works.

### 8. Keep it running: the watch folder (optional)

If your historian can export a CSV to a folder on a schedule, the tool can run shadow mode on each new export automatically. It is deliberately **not** a live plant connection: it only reads files that someone or something drops in a folder.

    .venv/bin/python -m aera.site watch my_works/site.toml --inbox /path/to/exports --candidate so_ref=1.7

What it does, and the promises it keeps:

- It looks at the inbox every 30 seconds (`--interval`). A CSV is only used once it has been untouched for 10 seconds (`--settle`), so a half-written file is never read.
- Each distinct file is run once. If the same file changes, it is run again. A file that fails (bad data, missing columns) is recorded as failed, the watcher carries on, and the failure is not retried until the file changes.
- The inbox is **read only**: it never changes, moves, renames or deletes your files and never writes anything there. It refuses to put reports inside the inbox.
- Reports go to `watch_reports/` next to your settings file (`--out` to change it): one folder per run, plus `index.html` (a table of every run), `latest_report.html` and `latest_report.json`.
- Every step is written to a tamper-evident log, `watch_audit.jsonl`, and each run keeps its own report and audit record.
- It makes no network connections and needs no passwords or keys.
- For a scheduled job (cron or Task Scheduler) use `--once`: it looks once, processes what is there, and stops.
- Stop it with Ctrl-C. Settings (`site.toml`) are re-read for every run, so you can change a consent or tariff without restarting.

Each run uses the normal window rule: it replays the longest continuous period in that file (up to 28 days, `--days`). To see the latest report in the web app, start the app with the environment variable `AERA_SITE_REPORT=/path/to/watch_reports/latest_report.json`.

### 9. Record a decision

If the recommendation is "ready for operator review", a named engineer should review it. Record the decision:

    .venv/bin/python -m aera.site approve my_works/shadow_report/report.json --name "A. Engineer" --note "Reviewed with the operators; trial step 1 on site"
    .venv/bin/python -m aera.site verify my_works/shadow_report/audit.jsonl

Every import, replay and approval is written to a log in which each line carries the hash of the one before. `verify` tells you if an entry was edited or deleted from the middle. Removal of the **last** entries cannot be seen from the log alone, so each run prints a short "audit record head": write it down somewhere else and later run `verify ... --head <that value>`. `approve` refuses a report that is not "ready for operator review" (unless you give `--override-reason`, which is recorded) and refuses a report that has been changed since the replay. **Approval is a record only; it changes nothing on the plant.**

## Permit limits

UK permits differ. The tool supports four shapes, each configured from your own permit:

| `kind` | Meaning |
| --- | --- |
| `absolute` | No sample may exceed the limit |
| `percentile` | The Nth percentile (usually 95) must not exceed the limit; optional `upper_tier` that no sample may exceed |
| `annual_mean` | The mean must not exceed the limit |
| `lut` | A look-up table: number of failures allowed for the number of samples taken. Copy the table from your permit as `lut = [[samples, failures], ...]` |

A "sample" in the model is a flow-weighted daily mean on your local calendar days, which stands in for a 24 hour composite. Set `sample_every_days` to mimic your actual sampling frequency: because you do not know which days will be sampled, the tool reports the **worst** of the possible sampling phases. A look-up table consent on a window shorter than its first row allows no failures and is marked indicative only. A suspended solids limit is only counted as checked if you also recorded effluent suspended solids. **Check the wording of your own permit; this tool does not replace reading it.**

## Settings reference

Everything is in `site.toml`. See the comments in the file written by `init`. The extra settings:

| Section | Setting | Default | Meaning |
| --- | --- | --- | --- |
| `[data]` | `max_fill_hours` | 2 | Gaps up to this long are filled by interpolation |
| `[data]` | `flatline_hours` | 6 | A value that does not change for this long is treated as a stuck sensor |
| `[data]` | `flatline_exempt` | none | Tags where a constant value is normal (for example a held lab result) |
| `[guardrails]` | `so_ref_min`, `so_ref_max` | 1.0, 3.0 | Allowed DO setpoint range for any recommendation |
| `[guardrails]` | `max_setpoint_step` | 0.5 | Larger changes are split into steps this size (shown only when a recommendation is ready) |
| `[validation]` | `nse_min`, `bias_max_pct` | 0.5, 20 | Pass marks for ammonium and energy |
| `[validation]` | `do_mae_max` | 0.3 | Pass mark for DO (average error, mg/l) |
| `[validation]` | `min_days_compared` | 7 | Fewest daily values an indicator needs before it can count |
| `[validation]` | `nh4_abs_bias_mg_l` | 0.3 | An ammonium bias this small (mg/l) passes even if it is a large per cent of a very low value |
| `[validation]` | `nh4_min_std` | 0.15 | Recorded ammonium that varies less than this cannot test the model |
| `[validation]` | `energy_factor_min`, `energy_factor_max` | 0.5, 2.0 | Believable ratio of your blower energy to the model's |
| `[calibration]` | `enabled` | false | Calibrate on every replay (or use `--calibrate`) |
| `[calibration]` | `train_fraction` | 0.6 | Share of days used to fit; the rest are held out |
| `[calibration]` | `min_improvement` | 0.10 | The fit is only used if it cuts the held-out ammonium error by this share |
| `[calibration]` | `flat_threshold` | 0.02 | A parameter whose 20% change moves the error less than this cannot be identified and is left at 1.0 |
| `[validation]` | `min_days` | 7 | Shortest period that can be replayed |

## Glossary

- **Activated sludge**: biological treatment where bacteria in aerated tanks remove ammonia and organic matter.
- **DO (dissolved oxygen)**: oxygen in the water, in mg/l. Too low harms nitrification and raises nitrous oxide; too high wastes energy.
- **Ammonium (NH4-N)**: the nitrogen the process must convert; usually the tightest permit limit.
- **Setpoint**: the DO value the controller aims for.
- **Nash-Sutcliffe efficiency (NSE)**: a score for how well a model follows measurements. 1 is perfect, 0 is no better than the average, negative is worse.
- **Bias**: the model's average error as a per cent of the recorded average.
- **Consent / permit limit**: the numeric limits on your effluent.
- **Percentile**: the 95th percentile is the value that 95% of samples fall below.
- **Composite sample**: a sample accumulated over 24 hours.
- **BSM1**: the IWA Benchmark Simulation Model no. 1, a standard activated sludge plant used to compare control strategies.
- **Shadow mode**: running a new idea alongside the real plant, on its data, without acting on it.
- **Validation gate**: the check that the model reproduces your records before its advice is allowed to count.
- **Temperature correction**: biological reactions run faster in warm water and slower in cold. The model scales its rates by typical coefficients (nitrifier growth changes about 10% per degree). It is exact at 15 degrees, where the benchmark was defined.
- **Warm-up**: the first days of a replay, where the model settles from its starting state; not counted.
- **Calibration**: adjusting two model multipliers (nitrifier activity, oxygen transfer) so the model fits your records better.
- **Held-out days**: days the calibration never saw, used to check that the fit is real and not memorised.
- **Identifiable**: a parameter is identifiable if your data can tell its value apart; if changing it makes no difference to the fit, it cannot be known from this data.

## Troubleshooting

| You see | Likely cause | Try |
| --- | --- | --- |
| `Cannot find site.toml` | Wrong path | Check the path you typed |
| `Column(s) [...] named in [data.tags] are not in the file` | A column name is misspelt | Names must match the CSV header exactly; the message lists the columns found |
| `Timestamp column ... is not in the file` | Wrong `timestamp_column` | Set it to your header name |
| `No rows with a readable timestamp` | Date format not recognised | Set `timestamp_format`, for example `"%d/%m/%Y %H:%M"` |
| `BSM1 archive not found` or a missing `.mat` file | The IWA files are not downloaded | Run `python scripts/fetch_bsm1.py` |
| Model "not validated" | See step 6 | |

## Limits you should keep in mind

Everything in this tool is a simulation of a generic plant. Before anyone changes a plant setting, a qualified engineer must decide on real evidence, and a controlled trial on your own works is the proper test. The tool is built to support that decision, not to replace it.
